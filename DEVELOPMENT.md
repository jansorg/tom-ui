# Development

`tom-ui` is a Qt 6 application built with CMake. At runtime it needs the [`tom`](https://github.com/jansorg/tom) command line application.

## Requirements

- CMake 3.16 or later
- A C++20 compiler: GCC or Clang on Linux, Xcode on macOS, MSVC (Visual Studio) on Windows
- Qt 6.4 or later with the modules Widgets, Svg, LinguistTools and WebEngineWidgets (WebEngine is only needed for reports, see `ENABLE_REPORTS` below)
- Linux only: Qt DBus (part of qt6-base) and the X11 development headers

### Ubuntu 24.04

```bash
sudo apt install cmake g++ make libgl1-mesa-dev libx11-dev \
  qt6-base-dev qt6-base-dev-tools qt6-tools-dev qt6-tools-dev-tools qt6-l10n-tools \
  qt6-webengine-dev qt6-webengine-dev-tools libqt6svg6-dev
```

### Arch Linux

```bash
sudo pacman -S cmake gcc qt6-base qt6-svg qt6-tools qt6-webengine libx11
```

### macOS and Windows

Install Qt with the [Qt online installer](https://www.qt.io/download-qt-installer) or [aqtinstall](https://github.com/miurahr/aqtinstall), including the Qt WebEngine, Qt WebChannel and Qt Positioning modules. Pass the Qt directory to CMake with `-DCMAKE_PREFIX_PATH=<Qt dir>`, e.g. `~/Qt/6.11.3/macos`.

## Building

```bash
cmake -S . -B build -DCMAKE_BUILD_TYPE=Release
cmake --build build --parallel
```

CMake options:

- `-DENABLE_REPORTS=OFF` builds without Qt WebEngine and without the report preview.

## Running

```bash
./build/tom-ui --tom /path/to/tom
```

- `--tom <path>`: path to the `tom` executable. On Linux the default is `tom` from `PATH`. On macOS and Windows, the default is the `tom` binary next to the `tom-ui` executable.
- `--configName <name>`: uses separate settings, useful to test without touching your own configuration.
- `--bash`: treat the `tom` executable as a Bash script.

## Global shortcuts

- X11, macOS and Windows: the native APIs of the platform are used (`qxt/`).
- Wayland: shortcuts are registered with the [XDG desktop portal](https://flatpak.github.io/xdg-desktop-portal/docs/doc-org.freedesktop.portal.GlobalShortcuts.html) (`portal/`). The desktop environment manages the actual key bindings; the shortcuts defined in tom-ui are only suggestions. This needs a portal with global shortcut support, e.g. KDE Plasma, GNOME 48+ or Hyprland. The app identifies itself as `tom-ui`, matching `resources/tom-ui.desktop`.

## Translations

Translations are stored in `translations/*.ts` and compiled into the application with every build. To update the `.ts` files after changing user-visible strings, run:

```bash
cmake --build build --target translations
```

Then translate the new strings with Qt Linguist (`linguist6 translations/tom_de.ts`) and commit the `.ts` file.

## Icons

`update-assets.sh` exports the SVG icons in `images/` to `resources/` and regenerates the application icons and `resources/resources.qrc`. It needs Inkscape, `rsvg-convert` (librsvg), ImageMagick (`magick`), Python 3 and optionally `optipng`.

The application icon is generated by `images/app-icon/make_svgs.py`, edit the script rather than the SVG files. It writes one SVG per platform:

| File | Used for |
|---|---|
| `tom-macos.svg` | `res/AppIcon.icns`: 1024 px canvas with an 824 px continuous-corner plate and a drop shadow, following Apple's app icon grid |
| `tom-windows.svg` | `res/AppIcon.ico` (48 px and larger, 256 px stored as PNG) and the window icon bundled in `resources/icons/tom*.png` |
| `tom-linux.svg` | hicolor icon `tom-ui` in `res/linux/` (scalable and 48-512 px), proportions of the GNOME icon grid |
| `tom-small.svg` | simplified variant for 16-32 px on all platforms except macOS |
| `tom-symbolic.svg` | monochrome `tom-ui-symbolic` icon for GNOME and KDE |

`images/app-icon/icon_pack.py` writes the `.icns` and `.ico` files, so `iconutil` or `png2icns` aren't needed.

The other icons in `images/icons/` use a 16 px grid and the colors of the application icon:

- Status and timer icons (`timer-*`, `project-active*`) are colored, coral for running and blue for stopped.
- Monochrome outline icons (`document-new`, `document-save`, `edit-delete`, `window`) are drawn in `#000000` with 1.2 px rounded strokes. `Icons::monochrome()` prefers the icon theme (system icons on Linux, SF Symbols on macOS and Segoe Fluent Icons on Windows with Qt 6.7+); the bundled fallback is recolored with the text color of the palette by `PaletteIconEngine`, so it works in light and dark mode.
- Tray icons: a running timer is shown as a red block on all platforms (`trayicon-started.svg`, `osx/trayicon-started.svg`). When stopped, `trayicon-stopped.svg` is a colored plate for Windows and Linux which works on light and dark panels, and `osx/trayicon-stopped.svg` is a template image (black and alpha only) which macOS colors to match the menu bar.

## Continuous integration

`.github/workflows/build.yml` compiles tom-ui and runs the tests with `ctest` (there are none yet) for every push to `master` and every pull request, on Linux (Ubuntu 24.04, Qt 6.4.2 from the Ubuntu packages), macOS (macOS 26, Apple Silicon, Qt 6.11.3) and Windows (Windows Server 2025, MSVC, Qt 6.10.3). It doesn't build packages.

`.github/workflows/release.yml` builds the release packages and creates a **draft** release:

| Platform | Release asset |
|---|---|
| Linux | `.deb`, depends on the `tom` package |
| macOS | signed and notarized `.dmg`, bundles `tom` and `tom-pdf` |
| Windows | unsigned application archive `tom-ui-<version>-windows-app.zip`, replaced by the signed installer by `sign-windows-release.sh` |

- The bundled `tom` binaries are taken from the latest [tom release](https://github.com/jansorg/tom/releases). A manual release can choose another release with the `tom-release` input.
- The release fails unless the bundled `tom` binaries are signed: a Developer ID signature on macOS (and arm64 binaries), an Authenticode signature on Windows.
- The macOS and Windows Qt versions are the latest that [install-qt-action](https://github.com/jurplel/install-qt-action) (aqtinstall 3.3) can install. Qt 6.12 changed the layout of its online repository, see [aqtinstall#1047](https://github.com/miurahr/aqtinstall/issues/1047). Update the versions in `build.yml` and `release.yml` once that's fixed.

## Making a release

1. Start the release workflow on `master`, either from the Actions tab ("Run workflow") or with:

   ```bash
   gh workflow run release.yml --ref master -f version=0.14.0
   ```

   If `version.txt` contains another version, the workflow commits the new version to `master`. It builds all packages, then creates the tag `v0.14.0` and a **draft** release with the Linux and macOS packages and the unsigned Windows application.

   Alternatively, set the version in `version.txt` yourself, commit it and push a tag `v0.14.0`. The workflow then releases the tagged commit; it fails if `version.txt` doesn't match the tag.

2. Sign the Windows release with the code signing certificate on the YubiKey:

   ```bash
   deployment/windows/sign-windows-release.sh v0.14.0
   ```

   The script signs `tom-ui.exe` of the draft release's application archive and replaces the archive. It then starts the `windows-installer.yml` workflow, which builds the installer from the signed application and attaches it to the draft release. Finally, the script signs the installer, replaces it in the draft release and removes the application archive. It asks for the YubiKey PIV PIN; touch the key if it blinks.

3. Review the draft release on GitHub and publish it:

   ```bash
   gh release edit v0.14.0 --draft=false
   ```

### Windows signing setup

The private key never leaves the YubiKey, which is why the Windows files are signed locally and not in CI. The signing script needs:

- [`gh`](https://cli.github.com/), logged in with access to the repository
- [jsign](https://ebourg.github.io/jsign/) 5.0 or later and Java
- `osslsigncode`, to verify the signatures
- `zip` and `unzip`
- the YubiKey PKCS#11 module `libykcs11` (package `yubico-piv-tool`)

Optional environment variables:

| Variable | Default | |
|---|---|---|
| `JSIGN_ALIAS` | `X.509 Certificate for PIV Authentication` (PIV slot 9a) | code signing certificate on the YubiKey, see `ykman piv info`. Slot 9c holds the Apple Developer ID certificate |
| `JSIGN_TSAURL` | `http://timestamp.sectigo.com` | RFC 3161 timestamp server |
| `JSIGN_CAFILE` | `/etc/ssl/certs/ca-certificates.crt` | CA bundle to verify the signatures |
| `JSIGN_PIN` | prompted | YubiKey PIV PIN |

The uninstaller written by Inno Setup at install time is not signed.

### macOS signing

The release workflow signs the app with the Developer ID certificate and the hardened runtime, notarizes and staples the disk image. It fails if the signing secrets are missing.

Repository secrets:

| Secret | |
|---|---|
| `MACOS_SIGN_P12` | Developer ID Application certificate with its private key, as base64 encoded `.p12` (`base64 -i cert.p12`) |
| `MACOS_SIGN_PASSWORD` | password of the `.p12` file |
| `MACOS_NOTARY_KEY` | App Store Connect API key (`AuthKey_<id>.p8`), its content or base64 encoded |
| `MACOS_NOTARY_KEY_ID` | ID of the API key |
| `MACOS_NOTARY_ISSUER_ID` | issuer ID of the API key |

The Qt WebEngine helper process is signed with the entitlements shipped with Qt (`QtWebEngineProcess.entitlements`). The bundled `tom` binaries keep their own signatures.
